MoE vs dense under load: 1 to 96 concurrent requests

Flint, a ~40B mixture-of-experts model run as NVFP4 W4A16 on Marlin kernels without torch.compile and on FlashInfer attention, against Qwen 3.8 27B, a dense model run as NVFP4 W4A4, compiled, on FlashAttention 2. Both were served by vLLM on one RTX PRO 6000 at 1 to 96 concurrent requests. The serving flags matched; the kernels and execution paths did not.

Workload: synthetic coding-agent chats with an 8K-token shared prefix and 14 turns. Each turn targets ~875 input and ~214 output tokens; the measured mean output was 241–357 tokens per level.

RTX PRO 6000 Blackwell Server Edition, 97,887 MiB · vLLM 0.32.1rc1.dev602+g5d35ce393 nightly (commit 5d35ce39) · 32K context · 1–96 concurrent requests · ~875 in / ~214 out per turn (measured 241–357 out) · n = 1 run per level

By Levi Le · 30 October 2026 · about $2.15 of cloud time

TL;DR

  • One request at a time: Flint (MoE) streamed 224 tok/s per request, Qwen (dense) 51.5 tok/s.
  • Total output, all requests: Flint reached 1,987 tok/s at 96 requests (server count 2,046) and was still climbing. Qwen levelled off at 675–687 tok/s from 48 requests (server count 670–701).
  • Within a latency SLO (p95 TTFT ≤ 1.5 s and p95 inter-token latency ≤ 50 ms): Flint held up to 64 concurrent requests, Qwen up to 16.
  • Compute cost at peak output: Flint $0.35, Qwen $1.01 per 1M output tokens (derived, compute only).
  • Not a pure MoE-vs-dense test: different model families, 4-bit recipes and kernels. Read the caveats before quoting.

Why it looks like this

Reading the curves

01 · ONE REQUEST

The MoE uses far fewer weights per token

Flint sends each token through 6 of its 256 experts plus a shared expert: about 2.5B of its 39.8B parameters. Dense Qwen uses all ~27B for every token. At one request, Flint streamed 224 tok/s and Qwen 51.5.

Sources: Flint's config.json (256 experts, 6 per token, shared expert), measured levels.

02 · MORE REQUESTS

The gap narrows as batches touch more experts

Every decode step serves the whole batch. With 6 experts per token, a batch of 43 tokens can already reach all 256 experts, so the MoE's per-token savings shrink as concurrency rises. Per-request speed went from 224 vs 51.5 tok/s at 1 request to 32.3 vs 15.5 at 48.

The expert count is an upper bound; how many experts a batch actually touched was not measured.

03 · QWEN PAST 48

A plateau, not a memory wall

From 48 to 96 requests, Qwen's all-request output stayed at 680, 687 and 675 tok/s (server count 694, 701, 670) while each stream slowed (median token gap 64, 81, 127 ms) and mean queue wait grew (0.26, 0.56, 1.49 s). The KV cache peaked at 75% and vLLM preempted nothing, so memory was not the limit.

GuideLLM's completed-only count fell (596 → 465) because unfinished long requests are omitted; counting them matches vLLM within 3%.

04 · FLINT AT 96

Headroom left

At 96 requests Flint's KV cache peaked at 51%, mean queue wait was 3.5 ms, and p95 time to first token was 0.31 s. The early-stop rule never fired, so its ceiling on this GPU is still unknown.

Sources: measured levels and vLLM metrics.

Caveats

Read before quoting these numbers

  • Not a pure MoE-vs-dense test. Different model families and different NVFP4 recipes: Qwen runs W4A4 on vLLM's FlashInfer CUTLASS FP4 kernels, Flint runs W4A16 on Marlin. vLLM logged that Flint would use "weight-only FP4 compression … leveraging the Marlin kernel".
  • Different execution paths. Flint ran without torch.compile (unsupported for this model) on FlashInfer attention; Qwen ran compiled on FlashAttention 2.
  • Responses ran longer than configured. The target mean was 214 output tokens; measured means were 241–357 per level. Both models used the same settings.
  • Requests are not users. Each stream sends its next turn as soon as the last one finishes, with no think time.
  • Single run, no repeats. No error bars.
  • No ceiling found. The early-stop rule (p95 TTFT above 10 s) never fired for either model.
  • Qwen's lower prefix-hit rate is partly by design. Its hybrid layers make vLLM use 832-token cache blocks (Flint: 16), and prefix caching reuses only whole blocks.
  • Uneven prompts at high concurrency. In each 120 s window Qwen's slower conversations reached fewer turns, so its mean prompt was shorter: 10,138 vs 14,538 tokens at 96 requests.

Not measured

  • Repeats: one run per level, so run-to-run variance is unknown.
  • A prefix-caching-off run, so the cache's share of these numbers is unknown.
  • Flint's saturation point: throughput was still rising at 96 requests.
  • GPU power cap and clocks.
  • Output quality: ignore_eos makes outputs fixed-length synthetic text.

p99 TTFT, p99 ITL and end-to-end latency (p50/p95/p99) were measured and are in the full table. At 1 request Qwen completed only 15 requests, so its p95 and p99 coincide.

Reproduce

Method

The runner script and CSV exporter live in my private lab repository. The settings below are the complete method; host, network and account details are left out. The raw data (GuideLLM reports, vLLM metrics and logs) is available on request.

Serving and load commands vLLM and GuideLLM 
vllm serve <model> \
  --tensor-parallel-size 1 --dtype bfloat16 --kv-cache-dtype auto \
  --max-model-len 32768 --max-num-seqs 512 --max-num-batched-tokens 8192 \
  --gpu-memory-utilization 0.90 --enable-prefix-caching --generation-config vllm
#   Qwen:  Inferact/Qwen3.8-27B-NVFP4 @ 6128240e, plus --language-model-only
#   Flint: RecursiveSI/flint-nvfp4-gguf @ 6ec43e19 (flint-nvfp4.gguf), with
#          --hf-config-path and --tokenizer from RecursiveSI/flint @ 2a247be0

# GuideLLM 0.8.0, once per level C in 1 4 8 16 24 32 48 64 96
guidellm run \
  --profile    "kind=concurrent,streams=$C,warmup=15" \
  --constraint "kind=max_duration,seconds=120" \
  --data "kind=synthetic_text,prefix_tokens=8000,prefix_count=1,turns=14,\
prompt_tokens=875,prompt_tokens_stdev=400,prompt_tokens_min=200,prompt_tokens_max=2000,\
output_tokens=214,output_tokens_stdev=250,output_tokens_min=50,output_tokens_max=1700"
# Requests: /v1/chat/completions, streamed,
#   temperature 1.0, top_p 0.95, top_k 20, ignore_eos true

Between levels the runner waits until vLLM reports no running or waiting requests. Metrics come from vLLM's /metrics (every 2 s) and nvidia-smi (every 1 s), cut to each level's window after warmup.
