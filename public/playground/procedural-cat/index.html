Can a 30B open model draw a cat?

This compares 4 models drawing a cat: Qwen 3.8 27B, Flint, Muse Glimmer 30B and Ornith 1.5 each got one try to draw a tuxedo kitten in pure Canvas JavaScript, served with vLLM on a single rented RTX 5090. No retries, no fixing their code.

Takeaways

Three things this run showed

In this run, a small-active MoE drew the best cat

Ornith 1.5 uses about 3B of its 35B parameters per token. With DFlash it reasoned for 21K tokens, finished in 70 s, and drew the most shaded, detailed cat. One sample per configuration cannot say whether the architecture caused that.

The original setup ran vLLM with --enforce-eager for memory safety. Qwen crawled at 8.5 tok/s while the GPU sat about 17% busy, waiting on kernel launches. vLLM's default CUDA-graph mode: 61.9 tok/s on the same model.

Why Qwen failed

It never stopped planning

Qwen clearly knew how: its reasoning contains about 67 canvas drawing snippets. It just never moved on to the answer. A follow-up run with Qwen's own recommended sampling (top_k 20, temperature 1.0) fixed the looping, but not the length.

Engineering log

What broke, and how it got fixed

Getting eight cold-started 30B models to run on one consumer GPU took more debugging than the benchmark itself.

01 · MEMORY

Muse DFlash ran out of memory while loading

Summing the checkpoint's tensor headers showed 28.4 GiB of weights on a 31.4 GiB card, including a 3.58 GiB vision encoder the text prompt never uses.

Fix: --language-model-only. It loaded and ran 3× faster than standard.

02 · SPEED

Eager mode was the bottleneck

Qwen decoded at 8.5 tok/s with the GPU about 17% busy, stalled on per-layer kernel launches.

Fix: vLLM's default compiled + CUDA-graph mode: 61.9 tok/s, 7.3×.

03 · HARDWARE

Two cloud hosts were broken

One returned CUDA unknown error for any GPU work while nvidia-smi looked fine; another couldn't start GPU containers at all.

Fix: a CUDA tensor check before downloading anything, and a driver that stops instead of burning a slot on a host fault.

04 · METHOD

A 300-second limit measured the wrong thing

The original design capped requests at 300 s and 6,144 tokens; Qwen spent all of it planning.

Fix: no time or token cap; measure the time instead.

05 · CONTEXT

8K context was too small

With a BF16 KV cache, Qwen MTP had room for only 18,521 tokens.

Fix: an FP8 KV cache, so 32K fits everywhere (Flint stayed BF16, see 07).

06 · MEMORY

Compiled warmup ran out of memory

With 32K FP8 KV reserved, warmup at an 8,192-token batch needed 544 MiB with 364 MiB free.

Fix: max_num_batched_tokens 2,048; prompts are far shorter.

07 · ENGINE

Flint rejected the FP8 KV cache

Its vLLM attention code hard-asserts BF16.

Fix: a recorded per-model BF16 exception; it still fits 32K.

08 · SAMPLING

Qwen looped

Under shared sampling it repeated the same design thoughts up to 9 times.

Fix: its publisher's top_k 20 removed the loop, and showed it simply needs more than 32K tokens here.

Limitations read before quoting these numbers
  • One sample per configuration. Another seed could draw a noticeably different cat, as the two Flint runs show.
  • Shared sampling for every model in the main run, not each publisher's recommendation.
  • All models are 4-bit quantized on one 32 GB GPU; full-precision or multi-GPU setups may behave differently.
  • Flint uses a BF16 KV cache while the others use FP8, because of an engine limitation.
  • Picture quality is judged by eye. Drawing-replay timing is normalized and is not inference speed.
  • Server startup (loading, compiling, graph capture: 1.5–4 minutes per model) is excluded from request timings.
